# 首轮数据采集与持续扩充约定

记录日期：2026-10-16。用于后续自主任务执行；本次记录范围与方案，不启动长期 goal，也不执行部署。

## 当前执行边界（最新授权，优先于早先纯离线限制）

- 用户已允许访问公开 GitHub，但明确禁止使用其个人身份、`gh` 或个人 API Key。此前“不访问 GitHub”的限制已被本条更新。
- 可用匿名 `curl` 或其他合理的匿名只读方式读取公开网页、API、README 和图片。不读取、探测或复用 `gh` 登录态、Token、浏览器 Cookie、Git 凭据或其他个人认证信息。
- 使用 curl 时以 `curl -q` 开始，禁用自动加载个人 `.curlrc`；不启用 netrc，不传认证头或 Cookie，不执行需要认证的远程 Git 操作。采集脚本不自动发现或读取环境中的个人 Token。
- 合理限速、缓存、断点续跑，遵守服务返回的限流及重试时间。限流时保存进度并等待，不轮换身份或 IP 来绕过限制。
- 先用隔离测试夹具验证采集流程；测试数值不得进入正式目录或当作真实采集结果展示。随后可按既定范围匿名读取真实公开数据，目标先达到 40 台设备 / 60 个项目，其他工作收敛后继续扩充。
- 仍仅完成本地可审阅结果，不部署、不发布、不向外部仓库写入、不联系作者。未来使用 GitHub Actions 或任何身份认证的自动化不包含在当前匿名采集授权中。

## 用户确认的范围

- 设备按厂商系统整理，以 ESPboards 的厂商/设备目录为发现起点，回查厂商资料。40 台是首个里程碑，不是最终上限；在其他任务完成、质量检查收敛后继续扩充。
- 项目先完成 60 个，再在其他工作收敛后继续扩充。优先从 M5Ware、awesome-esp32、ESPboards 等已有目录发现，再回查上游仓库；避免无方向地搜索。
- 每个厂商尽量完整，持续记录覆盖进度、已收录型号、待收录和待核验型号。40 台阶段不等于所有厂商已覆盖或每家都已收齐。
- 项目应有 README，入库时 Star 不少于 10；Star 只是最低筛选条件，还需核实项目用途和内容质量。
- 难以确认具体适配设备的项目可以待定，不为填充筛选结果强行关联。项目质量符合要求时，可先收录项目并将具体设备关联标为待核验。
- 允许根据采集需求调整内容字段、采集脚本和必要的页面读取逻辑，并同步文档。
- 仅做到本地可审阅，不部署、不发布，不向外部仓库提交内容或联系作者。

## 许可待澄清

用户提到“不一定有证书”，已单独询问是否指不要求独立 LICENSE 文件。澄清前沿用原有“项目必须开源”的要求：README 或其他上游位置明确许可也可作为依据；没有明确许可的先待核验，不直接标为开源。README 和 Star 门槛不代替许可判断。

## 厂商归属

已知厂商按稳定厂商 ID 分目录，显示名称规范化。没有明确品牌的通用板归为 `generic`（通用 / 无品牌）；暂无法核实实际厂商的记录归为 `unknown`（厂商待确认），与已知无品牌区分。不把芯片厂商 Espressif 自动当成整板厂商，也不把销售商或转售店铺自动当成制造商。型号别名、克隆与硬件版本需要去重或明确区分。

参考：ESPboards 本身也提供 Generic 分类：https://www.espboards.dev/esp32/ 。

## 采集台账方案

后续执行时在 `data/collection/` 保存结构化候选台账，并生成便于审阅的进度报告。现有样例也应登记，避免重复采集。

建议状态：`discovered`（已发现）、`pending`（待处理）、`needs-review`（待核验）、`included`（已收录）、`excluded`（暂不收录）。每条记录保留发现来源 URL、上游 URL、稳定 ID / GitHub 仓库身份、处理原因、核验日期；项目的设备关联可单独标为待核验。

按来源与厂商分别统计发现数、收录数、待核验数、排除数。中断或继续扩充时从台账恢复，不重复进行无记录的探索。所谓“完整”仅针对已经检查过的来源与核验日期，不保证覆盖互联网上全部硬件。

## Star 更新方案（尚未实现）

1. 入库时调用 GitHub 仓库接口，读取 `stargazers_count`，核验 README，并将采集结果保存至 `data/repository-metrics.json`；项目 Markdown 保留人工维护的内容，不写入反复变化的 Star。
2. 元数据以稳定项目 ID 为键，同时记录 GitHub 仓库身份、Star 和成功采集时间。采集失败保留上次有效值，不把失败当作 0，不伪造采集时间。
3. 网站构建时读取快照，展示数值和采集日期，并用于 Star 排序；用户浏览和切换筛选不请求 GitHub。
4. 本地审阅阶段提供可手动重复运行、支持断点与限速的采集命令。未来经用户另行授权并连接网站仓库后，可增加每日一次的 GitHub Actions，更新有变化的快照后构建部署；当前不启用身份认证的自动化或外部自动发布。
5. 后续确认 Star 跌破 10 的条目，建议移出公开列表并保留台账，进入待复核；接口失败不触发移除。该持续展示策略是实施建议，入库不少于 10 是用户已确认要求。
6. 首版只保存最新快照，不制作增长趋势榜；需要趋势时再增加历史记录。
7. `pushed_at`、仓库元信息更新时间、最新代码提交时间和本站采集时间分别理解，不能互相替代。

GitHub 未认证 REST 请求限制为每 IP 每小时 60 次；本地任务需限速并在限额耗尽后保留进度。未来如另行授权 GitHub Actions，可评估其内置 `GITHUB_TOKEN`，官方默认额度为每仓库每小时 1,000 次；当前只使用匿名访问。不在聊天、命令输出或公开数据中记录凭据。
